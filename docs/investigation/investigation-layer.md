# Investigation Case & Explainability Layer

This document outlines the architecture, data schemas, explanations, ranking rules, and validation mechanisms for the Investigation Case & Explainability Layer of Nirikshak AI.

---

## 1. Purpose & Core Principles
> [!IMPORTANT]
> **The Investigation Layer does not determine whether wrongdoing occurred. It organizes and explains anomaly indicators generated by the anomaly detection engine for human review.**
>
> It acts as a consumer layer, converting raw statistical triggers into human-readable investigation cases for auditors and investigators. It maintains strict immutability of the source code and results from the preceding steps.

---

## 2. Input and Output Datasets

### Input Files (Read-Only)
* `data/processed/anomaly_results.csv` (Tabular anomaly indicators and priority scores)
* `data/reports/anomaly_results.json` (Detailed evidence lists for each record)
* `data/processed/duplicate_pairs.csv` (Pairwise near-duplicate relationships)
* `data/processed/mplads_clean.csv` (Source fields and exact duplicate group IDs)
* `data/processed/mplads_features.csv` (Engineered features including convenience `work_type`)

### Output Files (Generated)
* `data/processed/investigation_cases.csv` (Flat, dashboard-ready representation of cases)
* `data/reports/investigation_cases.json` (Structured JSON representation with nested arrays)

---

## 3. Evidence Hierarchy & Tie-Breaking
For each flagged record (where `investigation_priority_score > 0`), the engine deterministically identifies the **primary indicator** using a two-level ranking:

### A. Severity Ranking
1. `critical` (Score: 4)
2. `high` (Score: 3)
3. `medium` (Score: 2)
4. `low` (Score: 1)

### B. Detector Tie-Breaker
In case of a severity tie, the following detector order is applied:
1. `exact_duplicate` (Score: 4)
2. `cost` (Score: 3)
3. `near_duplicate` (Score: 2)
4. `pattern` (Score: 1)

The evidence items are sorted descending by `(severity_score, detector_score)`, and the first item in the sorted list is selected as the primary evidence.

---

## 4. Explanations & Formats

### Case Title Generation
The case title is derived deterministically from the `primary_detector`:
* `exact_duplicate` ➔ `"Repeated Project Record Requires Review"`
* `cost` ➔ `"High-Cost Allocation Requires Review"`
* `near_duplicate` ➔ `"Potentially Suspicious Project Similarity"`
* `pattern` ➔ `"Unusual Recommendation Pattern"`
* Fallback ➔ `"Anomaly Flagged for Review"`

### Case Summary Format
A neutral, concise explanation combining the primary evidence message and total indicators:
```text
This project was flagged for review because [formatted primary evidence message]. It triggered [evidence_count] total indicator(s).
```

### Evidence Message Formatting Rules
Raw evidence items are transformed into user-friendly strings using `evidence_formatter.py`:
* **Cost**: `Allocation is [value]x the median amount among comparable [dimension] works.`
* **Exact Duplicate**: `This exact project record appears [value] times in the dataset.`
* **Near Duplicate**: `This project has a high contextual similarity with related project records.`
* **Pattern**: `This recommendation occurred during an unusually high concentration of recommendations within the observed 30-day period.`
* **Fallback**: Preserves the original raw evidence message.

### Mandatory Disclaimer
Every case contains a dedicated `disclaimer` field with the exact wording:
```text
Risk indicators identify records that may warrant further review. They do not establish wrongdoing or corruption.
```

---

## 5. Related-Record Logic
To avoid cluttering case payloads with thousands of template matches, only meaningful relationships are linked:
1. **Exact Duplicates**: Other records from `mplads_clean.csv` sharing the same `exact_duplicate_group_id` (excluding the current record).
2. **Potentially Suspicious Near Duplicates**: Pairs in `duplicate_pairs.csv` where `pair_type == "potentially_suspicious"`.
3. **Contextual Near Duplicates**: Pairs in `duplicate_pairs.csv` where `pair_type == "contextual_near_duplicate"`.

`template_match` relationships (highly similar text with no contextual overlap) are excluded from the investigation case outputs.

---

## 6. Deterministic Case Ranking
Cases are sorted globally by the following priority rules (descending):
1. `investigation_priority_score` (descending)
2. `highest_severity_score` (descending)
3. `allocation_amount` (descending, NaNs treated as -1)
4. `record_id` (ascending)

After sorting, a unique and contiguous 1-indexed `rank` field is assigned to each case.

## 8. Validation Rules
The pipeline enforces the following validation checks:
* **Integrity**: Every case has a valid disclaimer, valid priority score, and matching evidence counts.
* **Non-overlap**: Record IDs are unique. Related records never include the current record.
* **Exclusion**: Common templates are excluded from related records.
* **Ranks**: Ranks are unique and contiguous.
